# Changelog

All notable changes to imageconverter are listed here, newest first.

## Unreleased

- **Filmstrip thumbnails are fresh after an Overwrite originals run** (bug fix): a file rewritten in place (crop, rotate) kept its old picture in the filmstrip; its thumbnail is now loaded again. The histogram's help and the README say clipping is measured in sRGB, so Display P3 colours beyond sRGB show as clipped.
- **Every output is a card under the Output heading** (Johan): the main output's format, compression, ⓘ size estimate and Save to now sit in an **Output 1** card, the same collapsible card as the extra outputs, which follow as *Output 2*, *Output 3*, … (names you gave them before are kept). Closed, the card shows one line (format · quality · Save to); it starts open and remembers its state (key `mainOutputExpanded`). The "+" stays at the top right of the heading, **When finished** stays under the cards (it is for the whole run), and the collapsed Output panel's one line is unchanged. Texts that said "main output" now say Output 1: *Same as Output 1* (size), *Beside Output 1* (Save to), "Output 1 JPEG" in the ⓘ size box, "only Output 1 is written" (Skip extra outputs).
- **Command line and installer fixes** (bug check D): `SIGTERM` (`kill`, `timeout`) and `SIGHUP` (a closed terminal) now stop a `convert` or `jobs run` like Ctrl-C (clean stop, partial report, exit 130) instead of killing it with temp files left beside the outputs; a second signal of any of them removes the temp files this process is writing (never another process's) and exits at once with 130. `jobs run -- -nightly` runs a job whose name starts with `-`. `--variant` values may contain commas: `folder="/Photos/a, b"` (double quotes) or `folder=/Photos/a\, b` (`\,`); inside a variant value `\\` is a backslash and `\"` a quote (any other backslash stays), documented in `--help` and the README. When the update installed but the old version could not be moved to the Trash or removed (for example root-owned in /Applications), the installer service's reply now carries a note: the update sheet says "The update is installed. The previous version could not be moved to the Trash; it is still at …" and waits for **Relaunch** (also in About, in place of Check Now, until the app is relaunched) instead of relaunching at once (it was thrown away before). Core `UpdateInstallerProtocol.install` replies `(error, note)`, `FileCommitter.removeOwnTemps()`; CLI `InterruptPolicy`.
- **Fresh data after an Overwrite originals run** (bug fix): after a run that replaced originals in place (same name and format), the privacy chip and panel, the size estimate (ⓘ) and the metadata panel kept showing the old file (GPS still listed after "Remove these" → Run, or the reverse). They are now keyed by the file's version (`FileVersion`: identity, modification date and size), so a rewritten file is read again; the preview's shared decode and Vision detections use the same version.
- **Shortcuts actions run one at a time** (bug fix): several actions started together (a folder automation firing once per file) each ran a background batch at half the cores and memory at the same time, which could overcommit the app. They now wait their turn, first come first served (`AutomationQueue`); each still returns its own files, and one cancelled while it waits just leaves the queue.
- **Clean quits** (bug fixes): a Run Job action waiting for a queued run now gets "imageconverter is quitting." instead of never returning when the app quits; a Shortcuts action started after Stop and Quit is refused with the same message instead of starting a run that is cut off; quitting while an update is being installed (from the installer service call's start until it returns) asks first and only offers **Wait** (no Stop and Quit), so the app is never left half replaced (`QuitPolicy`).
- **A refused Resume keeps the interrupted batch** (bug fix): when Resume's run couldn't start (a folder wasn't allowed, or another conversion started first), the batch's journal and its own pipeline and output were silently lost. It is now kept, a toast says why, and the question is shown again (`ResumeStart`).
- **Nested conditions in a file no longer crash the app** (bug check, untrusted input): a preset, job or pipeline file with a condition inside a condition's branch was decoded to any depth before the nested one was dropped, so about 60 nested levels (an 11 KB file in the presets folder) overflowed a background thread's stack when an "Apply preset" action, a job or a Shortcuts action read it. A condition inside a branch is now recognised by its keys and left out without being read, and the app (at launch and when a preset is chosen), jobs (as a run problem) and the command line (as a warning) say "A condition inside another condition's branch was left out (conditions can't be nested)". Files with one level of condition load as before. Core `ConditionalStep.nestedConditionNote`, `NestedConditionCount`.
- **GPS inside XMP location structures is found and removed** (privacy fix): coordinates stored in IPTC Extension's Location Created / Location Shown (`exif:GPSLatitude`/`GPSLongitude` inside the structure, as Lightroom and Photo Mechanic write them) gave no privacy finding when the file had no GPS dictionary, so the suggestion didn't remove the location, and the metadata panel's "remove GPS position" left them in the output. The scan now lists every XMP tag holding coordinates ("GPS position in an XMP location", with its values and a link to its metadata-panel row), and the Metadata step's location removal (also when setting a new position), the suggestion and "remove GPS position" remove those tags, and ImageIO's IPTC-dictionary copy of a Location Created / Shown holding coordinates (which it otherwise wrote back as an empty structure). Core `MetadataOps.pathsHoldingGPS`/`removeTagsHoldingGPS`/`removeIPTCLocationsHoldingGPS`.
- **Metadata values can't break the output's XMP** (bug fix): a value with a Unicode noncharacter (U+FFFE, U+FFFF, U+FDD0–U+FDEF or a plane's …FFFE/…FFFF), typed, from a preset or from a source file's IPTC, made the whole XMP packet unreadable, so readers dropped the copyright, creator, alt text and keywords. Those characters are now removed from every value written (and XML-illegal control characters from IPTC values mirrored into XMP). Core `MetadataFields.xmlSafe`.
- **Rename keeps one separator between two empty tokens** (bug fix): `{date}_{camera}{lens}_{counter:00}` on an image without camera or lens metadata gave `1970-01-0107`, and `{date}{camera}_{counter}` gave `1970-01-017`; they now give `1970-01-01_07` and `1970-01-01_7`. An empty token at the start still drops the separator after it (`{camera}_{name}` → `IMG_1`). Text before an empty token now keeps the separator after it: `IMG{camera}_x` gives `IMG_x` (was `IMGx`).
- **Faster downsampled JPEG decodes, HEIC thumbnails and adding many files** (bug check G): the batch's reduced-size decode for a first-step resize asked ImageIO for twice the target, which for a JPEG is slower than a full decode unless it is source / 2^k (48 MP to 4096 px: 196 ms against 111 ms full). It now decodes at the smallest source / 2^k at least twice the target, or source / 2 when only the full size would be (never between source / 2 and the source); the resize still does the filtering. Measured (M5 Pro, release build, `BatchRunner.prepare`, decode + resize): 48 MP JPEG to 2048 px 216 → 75 ms, to 900 px 62 → 51 ms; 48 MP HEIC to 2048 px 135 → 127 ms, to 900 px 136 → 93 ms; 12 MP JPEG to 900 px 28 → 22 ms. Results differ slightly from before (PSNR 44–54 dB between the old and new output, 46–49 dB against a full decode). Filmstrip and watermark-chip thumbnails use the file's embedded thumbnail when it is at least the asked size and the image's shape (within 2 %; a differently shaped one may show the uncropped photo): a 48 MP HEIC with one 147 → 5 ms (no change for JPEGs or files without one; analysis, redaction and alt text copies always come from the image). Adding a folder with thousands of images changes the list once instead of once per file (quadratic on the main actor before), not at all when everything is listed already, and the files' identity checks run off the main thread. The Color step returns an image already in the chosen profile (sRGB or Display P3, 8/16-bit, opaque or premultiplied) as is instead of redrawing it (48 MP: 14–27 ms → 0). Core `ItemAdds`, `ImageLoader.thumbnailOptions`, `ImageOps.isAlreadyConverted`.
- **Clear stops a scan in progress** (bug fix): pressing Clear while "Adding…" showed brought the images back when the folder scan finished, and a scan that finished after a run started (from a service, script or link) added its images to the list mid-run. Clear now drops scans in progress, and a scan that ends during a run is added when the run ends, with a toast ("Added 12 images that arrived during the run").
- **Previews show sooner** (Johan: "load time takes a long time … make the app more responsive and fast"): clicking another image no longer waits the 300 ms meant for slider edits (the size estimate no longer waits 400 ms); edits keep their 300 / 400 ms. For a pipeline whose look doesn't depend on the pixel count (Adjust without Sharpen, Noise reduction, Shadows or negative Highlights, Color without Reduce colours, 90° turns and flips, Resize by percentage, edge or fit; no Crop, Canvas, Perspective, Trim, Watermark, Redact or conditions) the preview first shows a quick proxy from a copy decoded at display size (at least 1600 px; a JPEG at source / 2^k, which ImageIO decodes cheaply), marked "Refining…" in the header, then the exact full-size render replaces it; while a slider moves only proxies are drawn, and the exact render runs 300 ms after the last edit. The settled preview is always the batch's result fitted for display. The size estimate (and the quality comparison) now take the preview's full-size decode instead of decoding the file again, also for the comparison original after a downsampled decode; a decode in progress is shared. Measured on an M5 Pro, release build, synthetic 48 MP JPEG, Adjust without sharpening: select → first image 300 ms wait + 253 ms → 71 ms (exact image 634 → 261 ms with the estimate running alongside), estimate 825 → 395 ms, slider edit → image 300 ms + 103 ms → 11 ms (proxy); with Sharpen (no proxy) select → image 680 → 314 ms and the estimate 882 → 449 ms. Core `PreviewTiming`, `PreviewProxy`, `Pipeline.isScaleInvariant`, `PreviewRenderer.renderProxy`, `PreviewResult.isProxy`, `SourceCache` (`PreviewCaches.sources`); tests `PreviewProxyTests`.
- **Redact previews load faster** (Johan: "load time when having redact active takes a long time"): the preview, the size estimate and the quality comparison each ran their own Vision detection on a new image (they shared no work in progress, and Vision doesn't run them in parallel): on a 48 MP photo with text that took 5.3 s (8.2 s with Compare quality open) where one detection takes 2.9 s (measured before the fix). A detection in progress is now shared by every lookup for the same image and step input, for Redact and for Crop / Resize fill focus alike. It runs on its own at user-initiated priority, so a render cancelled by the next edit or selection doesn't stop it for the others; when no one waits for it any more it keeps running for 2 s, so the next edit's render (300 ms later) picks it up, and is cancelled only if nobody did. A batch start cancels detections nobody waits for. A failed detection still fails every waiting render closed and isn't kept, so the next one tries again. While the preview waits, its header says "Finding faces and text…" ("Finding faces…" / "Finding text…"). Core `SharedDetections`, `RedactTarget.findingStatus`, `FocusContext.redactActivity`; tests `DetectionCacheTests`.
- **Concurrent runs never replace each other's files** (bug fix, "never lose files"): two runs at once into one folder (a manual run next to a job, several Shortcuts actions, a Service, a script or the command line) planned the same names, and the second either failed its files ("an item with the same name already exists") or, when the moves overlapped, silently replaced the other run's outputs (in overwrite mode with a new name or format both originals were trashed too). Every commit is now an exclusive rename (`renamex_np` with `RENAME_EXCL`): when something has the planned name, the file takes the next free `_2`, `_3`, … (up to 1 000 more names), and the report, the job ledger, Finder tags, file dates, "When finished" and the original's trashing follow the name really written. Runs in the app also hold the names they planned until each file is done (`PlannedDestinations`), so two runs don't plan the same name; extra outputs and jobs' report files are written the same way. Core `PlannedDestinations`, `OutputNaming`, `FileCommitter.commit` returns the written URL; tests `ExclusiveCommitTests`.
- Commits on volumes without exclusive rename (exFAT USB sticks and SD cards, some network volumes) reserve the name with an exclusive create first and then move the file over that placeholder, so they are written as before and still never replace anything (tested on an exFAT disk image).
- A *Copy original unchanged* in overwrite mode whose original can't be moved to the Trash afterwards is now a written file with a warning ("Converted, but couldn't move the original to the Trash: …"), like a converted file; it was listed as a failure before.
- **Long names are shortened instead of failing**: a source name near the 255-character limit plus the same-folder suffix, a `_2` or a longer extension (png → jpeg) failed with "the file name … is invalid"; the name is now cut at the end (on a character boundary) so the whole name fits (counted as APFS counts: UTF-16 units of the decomposed name, so "é" counts 2 and "ǘ" 3), always keeping at least the name's first character. The same-folder suffix also drops zero-width and bidi characters and is capped at 64 of those units. Tests `LongNameTests`.
- **Redact's size sliders work on every photo** (Johan: "when dragging the slider the pixel size is not changed"): Pixelate's fixed 4–256 px block size was raised to the privacy floor (a fifth of each area's shorter side) on full-size photos, so for a face on a 24 MP photo every size from 4 to 200 px drew the same pixels. The control is now relative to each area: Pixelate's **Blocks across**, Coarse (2) to Fine (5) blocks across each area's shorter side, and Blur's **Strength**, Light (a radius of 1/5) to Strong (1/2); Auto (3 blocks across / a radius of 1/3, as before) and a double-click goes back to it; 5 is the floor, so nothing is weaker than before. Saved as `blocksAcross` / `blurAcross` only when not Auto. Steps saved with a pixel size (`blockSize` / `blurRadius`) keep drawing exactly as before; the editor shows "Saved as 16 px; move the slider to switch" and the preview header shows the "Block size raised to keep 1 area unreadable" note. Summaries read "faces · pixelate · 2 blocks across" / "faces · blur · radius 1/5 of each area". Core `RedactOptions.blocksAcross`/`blurAcross`/`withAcross`, `PreviewResult.redactSizeNote`; tests `RedactBlockSizeTests`.
- **Redact finds text on transparent backgrounds** (privacy fix): Vision reads transparent pixels as black, so black or dark text on a transparent PNG (a signature, a cut-out label, a form saved with alpha) was found nowhere and written readable with "Redact: nothing found". An image with transparent pixels is now read for text on two flattened copies, onto white and onto black (the ≤ 2048 px copy and every full-resolution tile), with the boxes joined and counted once; faces on a copy flattened onto mid grey. The privacy panel's faces/text check uses the same detection. Images whose pixels are all opaque (PNG screenshots with an unused alpha channel too) are read once, as before: the ≤ 2048 px working copy's alpha is scanned once (area-averaged downsampling, so one transparent pixel of a 16 000 px image still shows). Core `VisionInput.prepared(_:maxSide:background:)`, `VisionInput.textBackgrounds`/`faceBackground`/`textBackgrounds(forCopy:)`; tests `RedactTransparencyTests` (real Vision, skipped without it).
- **Histogram and clipping in the preview**: a chart button in the preview header (View ▸ Show Histogram, ⌥⌘G) shows the RGB and luminance histogram of the Original or the Result (remembered) in the preview's corner, measured on the preview image (≤ 1024 px) after each render, scaled to the 99.5th percentile bin; "Highlights x.x %" and "Shadows x.x %" turn red above 0.1 %. View ▸ Show Clipping (⌥⌘J), or a click on either figure, marks clipped highlights red and crushed shadows blue over the result in side by side, split and single mode, following the zoom. Both off by default (keys `showHistogram`, `showClipping`, `histogramSource`). Core `ImageHistogram` (`compute`, `clippingMask`, `displayPeak`); `PreviewResult.beforeHistogram`/`afterHistogram`.

## 1.4.0 (2026-11-16)

- Shortcuts actions: they run with the background limits jobs use (half the cores, half the memory budget; `BatchResourceLimits.background`); each converting action is recorded in History ("Shortcuts: *preset*") and quitting waits for it like for a batch (`AutomationRuns`); copies of data Shortcuts passed are removed when the action ends and capped at the decode limit's 2 GB; a preset whose extra output saves beside the originals stops with the Folder Access message when that folder isn't allowed (it failed per file before); job names reach Siri and Spotlight phrases (`updateAppShortcutParameters` at launch and after a preset or job changes). Run Job's summary reads "Job Web export: Converted 12 · 1 skipped by a condition" (`Automation.jobSummary`, tested). Resize Images never enlarges; every action writes the first frame of animated and multi-page files (README).
- Extra outputs' folders: a folder you choose again in Run's open panel is written to even when no bookmark could be made for it (it was refused with a note before; `VariantFolderPolicy.confirmedOr`); two outputs that share a folder to choose again ask once; the panel flags a confirmed folder again when it has been deleted since; `imageconverter jobs run` names every extra output's folder first, like `convert`; a resized PNG extra output of a reduced-colour image says "this output's size change added colours" instead of blaming a later step.
- **Warm Adjust looks are golden**: Golden Hour, Vivid Warm and Dramatic Warm use much more warmth, a little magenta and less vibrance (which pulled skies and grass back to blue and green); on the sample meadow and sunset photos the mean red minus blue now rises by 20–39 levels and nothing turns greener (`AdjustWarmLooksTests`).
- **Adjust sliders with 0 in the middle** (every −100…+100 slider and Hue) now fill from the centre to the knob, like Soft ↔ Sharp; the fill ends exactly under the knob's centre (the knob's inset travel is taken into account), the neutral tick is drawn over the fill and the track is easier to see. The slider is called **Soft ↔ Sharp** everywhere (editor, step summary help, README).

- **Shortcuts actions** (Johan): imageconverter now shows up in the Shortcuts app, Spotlight and Siri with seven App Intents actions: **Convert Images** (images, a preset chosen from suggestions of the built-in and saved presets, optional format and output folder), **Apply Preset to Folder**, **Run Job** (a saved job, chosen from suggestions; waits for the run and returns a summary), **Strip Metadata**, **Resize Images** (long edge), **Convert Format** (format, quality 1–100) and **Get Image Metadata** (text), plus App Shortcuts phrases ("Convert images with imageconverter", …). They run inside the app without opening its window (`openAppWhenRun = false`), return the written files, never change originals and never replace existing files. Without an output folder the files go to a scratch folder in the app's temporary folder (older than a day: removed) and are only returned; a folder (input or output) must be allowed in Help ▸ Folder Access, otherwise the action fails with a message saying so. Errors are plain sentences in Shortcuts (unknown preset or job, no files, no images, a format this Mac can't write, every image failing with the first reasons). Presets and jobs are matched by name like scripts, links and the command line. Before, the app had no `Metadata.appintents`, so Shortcuts listed nothing. Core `Automation` (`AutomationRequest`, `AutomationResult`, `AutomationError`: the actions' logic through `BatchRunner`, tested without Shortcuts) and `PipelineOverrides` (the command line's `--format`/`--quality`/`--max-size`/`--resize-long`/`--variant`/`--strip-*` overrides, now shared with the actions); app `Sources/Imageconverter/Intents/` and `JobsController.runNowAndWait`.
