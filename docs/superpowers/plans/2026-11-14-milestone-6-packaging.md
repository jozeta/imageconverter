# Milestone 6: packaging, sandbox, About, release script, screenshots

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the SwiftPM build into a sandboxed, signed-ready `.app` with an About window, working sandbox file access (bookmarks for every remembered file/folder), Services/AppleScript/URL registration, a bundled CLI, an icon, a release script that can sign and notarize (run only with Johan's credentials and consent), and README screenshots.

**Architecture:** `scripts/release.sh` assembles the bundle from `swift build -c release` products; Info.plist is generated from `VERSION` + `Resources/Info-fragments.plist`; entitlements in `Resources/imageconverter.entitlements`. Sandbox access is centralised in Core `FolderAccess` (exists, Task 31) and a new app-side `AccessStore` for user-granted folders. Local builds sign ad hoc; Developer ID signing and notarization only when `SIGN_IDENTITY` / `NOTARY_PROFILE` are given.

**Tech Stack:** Swift 5.10 SwiftPM, AppKit/SwiftUI, codesign, notarytool, stapler, iconutil, plutil (all Apple tools).

**Spec:** `docs/superpowers/specs/2026-11-13-imageconverter-design.md` (Tech: Distribution; App Sandbox; version in About).

## Global Constraints

- Apple frameworks and Apple command-line tools only; no third-party code.
- App Sandbox ON: `com.apple.security.app-sandbox`, `com.apple.security.files.user-selected.read-write`, `com.apple.security.files.bookmarks.app-scope`; NO network entitlement; hardened runtime with no exceptions.
- Bundle identifier `io.github.jozeta.imageconverter` (Claude's call; GitHub user from CLAUDE.md; change in one place: `scripts/release.sh` `BUNDLE_ID`).
- Credentials never in the repo: signing identity and notary keychain profile come from environment variables; the script never prints secrets.
- Never run `--notarize` or a real Developer ID signature in this milestone without Johan saying so; local verification uses ad-hoc signing.
- Version: one source, `VERSION` (0.1.0 now; bumped to 1.0.0 only in the commit that is pushed).
- Build 0 warnings, all tests green, `swiftlint --strict` 0 violations; commit trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; stage only files you changed.

## Review Focus

1. A sandboxed build dropped a single file and run in "Same folder" or "Overwrite" mode must ask for the folder once (pre-filled panel) and then work; the grant must survive relaunch.
2. Presets/templates/jobs/pipeline that reference a watermark image or output folder must keep working after relaunch in the sandbox (bookmarks), and degrade with a clear message when the file moved or access is gone.
3. The CLI shipped in the bundle must find the same presets/jobs as the sandboxed app (container path) without breaking unsandboxed `swift run` use.
4. The release script must fail loudly (non-zero) on any step error and never leave a half-signed bundle looking finished.
5. Resume after a crash in the sandbox must regain access to the journal's files/folders (bookmarks) or explain why it can't.

### Task 7: Overwrite with rename (Johan, 2026-11-14)

Johan asked for either a new Save-to option or changed overwrite behaviour so renamed files replace their originals. Controller decision: change "Overwrite original files" to allow the Rename step.

Rules (Core OutputPlanner + callers):
- Overwrite + rename active: the output goes into the source's own folder under the rendered name (+ the output format's extension). If that path is the source itself (same name and extension, case rules per FileIdentity) → in-place replace (as today). Otherwise → write the new file, then move the original to the Trash only after the new file is committed (existing `trashesSource` path). Never replace any other existing file: a clash with an unrelated file, or with another item's planned output, gets `_2`, `_3`… (existing collision rules). Two items renamed to the same name → `_2`.
- An item renamed onto ANOTHER item's source path (e.g. a.jpg→b.jpg while b.jpg is also in the batch) must not overwrite that other source before it is processed: treat other items' sources as claimed (they are pre-claimed today outside overwrite; extend to overwrite for non-self paths) → gets `_2`.
- Undo the Task 1/Task 4 restrictions: OutputPlanner no longer ignores baseNames in overwrite; the Rename row and "+ Add step › Rename" are enabled in overwrite mode; remove the "Not available when overwriting originals" texts. The overwrite confirmation text (Save-to selection and external confirmations) says: "Converted images replace the originals. When the name or format changes, the original is moved to the Trash after the new file is saved."
- Everything that plans goes through the same planner: batch, preview name, size estimate, CLI (`--overwrite` + rename via preset/pipeline) and dry-run, conditions (`.rename` overrides, copyOriginal in overwrite = no-op stays), jobs (overwrite jobs: renamed outputs must be recorded as outputs in the ledger so they aren't re-processed as new inputs — check ProcessedLedger outputs table), resume (an original that was trashed is "done": the journal's I1 rule treats missing/changed sources as done with a notice — verify for the trashed case), the busy registry, the report (destination = new name).
- Tests (fail-first): overwrite+rename writes new name and trashes original (injected Trasher); rename to the same name replaces in place; clash with unrelated existing file → `_2`, unrelated file untouched; a→b while b is in the batch → `_2`, b processed normally; two items to the same name → `_2`; CLI dry-run shows the renamed destinations with "replace (original to Trash)"; job overwrite+rename doesn't re-process its outputs on the next run; resume after crash between commit and trash doesn't duplicate (document the existing m4 behaviour if unchanged).
- README (Save to table, Rename section), CHANGELOG, in-app help text.
